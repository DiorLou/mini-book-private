# 笔记内容标准

## 推荐结构

根据内容裁剪结构，但不可省略“问题背景”“机理讲解”和“回到问题”。

```markdown
# 专有名词：具体问题或结论

## 问题背景

说明读者当时在做什么、看到了什么现象、原本期待什么，以及因此产生的具体疑问。

## 一个具体例子

整理用户给出的代码、数据、报错或业务情境。只补充帮助阅读的名称和说明，不改变事实。

## 核心知识与机理

### 专有名词一

先用日常语言解释，再说明它在本例中的作用、因果链和边界。

### 专有名词二

需要时继续拆分。

## 回到原问题

逐步说明上述机理如何导致例子中的现象，以及应该如何判断或处理。

## 要点小结

- 可复用的判断原则
- 容易混淆的边界
```

## 背景重建规则

- 将散落在多轮提问里的环境、目标、已尝试方法、实际现象和预期现象合并起来。
- 代码很长时只保留能触发现象的最小片段；用注释交代省略内容。
- 用户没有提供可执行例子时，可以用贴近原场景的“示意例子”，但必须明确称为示意，不得冒充用户的真实代码或数据。
- 报错信息保留关键句，并解释它指向哪个环节，不堆贴整段日志。

## 知识强调规则

- 首次出现写作 `**专有名词（英文或缩写）**`，随后立刻用一句白话解释。
- 小标题优先使用专有名词，并用冒号连接它解决的具体问题。
- 强调因果关系：不要只写“是什么”，还要写“由于什么机制，因此出现什么结果”。
- 明确适用条件和反例。若结论只适用于特定语言版本、框架、市场或配置，必须写出范围。
- 不用大量加粗制造噪声；只强调核心术语、关键因果和最终判断。

## 质量检查

完成前逐项确认：

- 不看原对话也能知道疑问从何而来。
- 示例足以复现或想象问题。
- 每个关键术语都有通俗解释。
- 读者能说出结果背后的机理，而非只记住结论。
- 知识已经重新作用于原例，形成闭环。
- 标题可检索，小标题醒目且具体。
- 没有虚构用户事实，也没有遗留聊天口吻。
